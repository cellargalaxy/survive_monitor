## 一、已修复

### 1. 【告警去重】落快照之后才写的告警/恢复记录，对端要晚一轮才看得到（中）

**依据（已确认）**
- `service/service.go` `monitor` 的顺序是：`view.SaveSelf`（写 `selfSnapshot.Time`）→ `view.Merge` → `alarmUrl` → `alarmResource`
- `alarmUrl` 发送成功后调 `view.SaveAlarm` / `view.RecoverAlarm`，修改前这两个函数只改 `Alarms` / `Recovers`，**不动 `Time`**
- 对端合并时 `service/view/view.go` `merge` 只收产生时间更新的快照：`if ok && old.Time >= snapshot.Time { continue }`

**后果**：对端在本实例 `SaveSelf` 之后、发告警之前拉过一次视图，之后再拉到带告警记录的那份，`Time` 没变，会被当成同一份旧快照丢掉，要等本实例下一轮 `SaveSelf` 才看得到。这一轮里对端的 `view.GetAlarm` 看不到「已经发过」，同一事件的离线告警、恢复通知就会再发一遍。各实例之间的去重本来就是这个服务的核心设计（`Snapshot.Alarms` / `Snapshot.Recovers`），这里等于平白把去重窗口拉长了一轮。

**修复**：`service/view/view.go` 新增 `touchSelf()`，让产生时间严格递增（`max(now, Time+1)`）；`SaveSelf`、`SaveAlarm`、`RecoverAlarm` 都调它。
- 时间戳是秒级的，发送和落快照常在同一秒，所以必须「+1」才能保证严格递增；`SaveSelf` 也走同一个函数，否则下一轮落快照时会被拉回 `now`，对端反而把新快照当旧的丢掉
- 不需要推进的：`SaveResourceAlarm` / `DelResourceAlarm`（资源告警只看本机记录，对端不用）；`Clean` 里删已恢复的告警记录、删用完的 `Recovers`（对端不拿到这些删除也不会算错）
- 顺带的好处：本机时钟往回跳时，产生时间仍然单调递增，对端不会在时钟追平之前一直丢弃本实例的快照
- `model/snapshot.go` `Snapshot.Time` 的注释同步更新

### 2. 【资源/压力】探测时把响应体整个读进内存，没有上限（中）

**依据（已确认）**：修改前 `probe/probe.go` 用 `response.Body()`，resty 默认会把响应体整个读完；判活只看响应码，响应体只拿来 `ParseView`。

**后果**：探测的 URL 返回的是大文件（下载地址、大页面）时，每轮都要整个下载一遍，内存跟着涨，也给被探测的服务添了压力。这和你在前几轮把探测改成串行时「不想增加服务压力」的初衷是相反的。

**修复**：`probe.Probe` 改成 `SetDoNotParseResponse(true)`，由这里用 `io.LimitReader` 最多读 `maxBodySize = 4MB`，读完立即 `Close`。
- 判活语义不变：读响应体时出错（超时、连接中断）仍然按失败计，和原来交给 resty 读时一样；单次超时 `probe_timeout_sec` 照样覆盖读响应体的时间（resty `SetTimeout` 设置的是 `http.Client.Timeout`）
- 超过上限的响应被截断，截断的内容解析不出视图，就当普通 URL「只知道它活着」。视图载荷只有几 KB 到几十 KB，4MB 足够宽裕

### 3. 【配置约束】按轮数过期之后，过期轮数配得太小会让对端的票时有时无（低，只加 Warn）

**依据（已确认）**：过期按**本实例**的轮数数（`view.expire`），而对端多久产出一份新快照，取决于**对端自己**一轮有多长。一轮 ≈ URL 数 ×（间隔 + 单次探测耗时）+ 间隔。URL 数多时，URL 全都超时的对端，一轮约是 URL 全都秒回的本实例的 `(间隔+超时)/间隔` 倍。

**后果**：`snapshot_expire_round` 不大于这个倍数时，对端快照在本实例这里会周期性过期又复活。离线判定要求「有结论的实例全体一致」，对端那张「在线」票一缺席，本实例单方面判离线就会告警，票回来又发恢复，来回刷。

默认值 `2s` 间隔、`5s` 超时、`5` 轮：倍数 3.5 < 5，安全。只有调大超时或调小过期轮数时才会出现，所以**只加提示，不改行为**：`config/config.go` 新增 `expireRoundTooSmall`，`Parse` 里满足 `snapshot_expire_round × probe_interval_sec ≤ probe_interval_sec + probe_timeout_sec` 时 Warn「加载配置，快照过期轮数偏小，对端探测变慢时会被误判过期」。

## 三、知道但不改的（影响小，或者属于有意的设计）

| 项 | 说明 | 不改的理由 |
| --- | --- | --- |
| 对端可以影响判定 | 任何被探测的 URL，只要返回符合格式的视图，就能投「在线」票压住告警，也能塞入 `Alarms` / `Recovers` / 任意数量的身份键（`expiredTimes` 不清理） | 被探测的 URL 都是你自己配的，信任模型本来就是「配置里的实例可信」，`handler/view.go` 也明确不做鉴权 |
| 重启后约 5 轮内有一张自己的旧票 | 重启后 `selfId` 换了，对端转发回来的「重启前的自己」不会被认成自己，会以对端身份在判定里投票，直到按轮数过期（默认 5 轮） | 时间很短；那份旧快照里的告警记录反而让告警在重启前后连得上 |
| 同一实例被两个 URL 指向时会算两票 | 去重只认 `selfId`，对端之间不按 `Id` 去重 | 「离线要全体一致、在线有一个就算」这两条，重复一票都不改变结论，只影响「N个实例确认」里的数字；而且配置约定所有实例共用同一份 URL 列表 |
| 根路径 `/` 是 404 | 看板在 `/static/` 下 | 和 jotcash 的做法一致，而且你是通过反代子路径访问的 |
| `install-docker.sh` 会把 `wx_secret` 明文回显 | 方便确认传参 | 个人部署脚本，在本机终端执行 |
| 明细裁剪每轮复制整段切片 | `trimRecords` 在窗口满了之后每次裁掉 1 条都要复制一遍 | 7 天窗口下单个 URL 也就几 MB，开销可以忽略 |
