# 对话1：board_url 与微信消息文案

## 一、背景调研（已确认）

- 微信发送统一走 `util.SendWxMsg(ctx, url, text)`（go_common `util/wechat.go:250`），`url` 落到模板消息的 `req.URL`（点开消息跳转的链接），`text` 落到模板字段 `te`；`sn`/`ip`/`lg` 由 go_common 自动填
- 本项目三处调用，`url` 都传的是 `""`：
  - `service/alarm.go` `alarmUrl`：服务离线/恢复
  - `service/alarm.go` `alarmResource`：资源恢复、资源超阈值
- 原服务告警正文格式：`服务离线\n<url> (N个实例确认，始于…)`。首行只有「服务离线」四个字，具体哪个 URL 全在第二行之后
- 配置都走 `model.Config` + yaml（`resource/survive_monitor.yaml`），`Monitor` 每轮现读配置（`service/service.go` `Monitor`），所以新加的配置项改完不用重启

## 二、方案与取舍

### 2.1 board_url 放在哪

- 做成 `model.Config` 的配置项 `board_url`，不做环境变量：项目里业务参数全在 yaml 里，环境变量只放 `wx_app_id`/`wx_secret` 这类密钥（见 `261001-213931-answer.md` 的裁决，已与 `config/config.go` 核对过）
- 允许为空：不设默认值，`fillConfig` 不兜底；为空时 `SendWxMsg` 收到 `""`，和改动前一模一样（消息不带跳转）
- `Parse` 里 `strings.TrimSpace`，和 `cleanUrls` 的处理一致，避免首尾空白导致跳转链接打不开
- 三处 `SendWxMsg` 都传 `conf.BoardUrl`：需求写的是「发送微信消息的时候」，资源告警也是微信消息，点开同样该到看板

### 2.2 文案为什么这样改

「只有一句服务离线」说明你在微信里实际只看到了首行。**原因待确认**，我能想到两种可能：

1. 微信模板消息对 `te` 字段的展示有限制（不渲染换行或截断长度），后面几行没显示出来
2. 消息正文是完整的，只是首行信息量太少

这两种情况我都不能根据代码下结论，所以按两种都兼容来改：

- **首行自成摘要**：离线几个、恢复几个、分别是哪些 URL。就算只显示首行，也能知道是什么出了问题
  - 摘要里的 URL 去掉了 `http://`/`https://`（`trimScheme`），协议头区分度低，摘要越短越不容易被截断；明细里的 URL 是完整的
  - 顺序和配置里的 URL 顺序一致（`saves` 是 map，按 `conf.Urls` 取）
- **明细补充字段**（数据全部来自现有 `model.Alarm`，没有新增存储）：

| 类型 | 原有 | 新增 |
|---|---|---|
| 服务离线 | URL、确认实例数、始于 | 已持续多久、第几次提醒(`SendCount`)、仍离线多久后再提醒(`getBackoff`) |
| 服务恢复 | URL、离线多久 | 始于、共提醒几次 |
| 资源超阈值 | 超出项及阈值 | 首行带当前 CPU/内存/磁盘，已持续多久、第几次提醒、下次提醒间隔 |
| 资源恢复 | 当前 CPU/内存/磁盘 | 超阈值多久、始于、共提醒几次 |

实际生成的样例（临时测试跑出来的输出）：

```
服务离线1个：s1.example.com/api/view；服务恢复1个：s2.example.com/
离线 https://s1.example.com/api/view：1个实例确认，始于2025-10-02 13:23:20，已持续6分钟，第2次提醒，仍离线则30分钟后再提醒
恢复 https://s2.example.com/：离线1小时6分钟，始于2025-10-02 12:23:20，共提醒3次
```

资源告警（按格式手写的示意，不是实际运行输出）：

```
资源超阈值：CPU 95.0%，内存 40.0%，磁盘 30.0%
CPU 95.0% (阈值90.0%，共2核)
已持续5分钟，第2次提醒，仍超阈值则30分钟后再提醒
```

说明：「始于」是告警记录的 `StartTime`，也就是首次发出告警的时间，不是第一次探测失败的时间（和改动前的含义一样）。

### 2.3 副作用评估

- 告警判定、退避、记录写回的逻辑没动，只改了文案拼接和 `url` 参数
- `judgeAlarm` 签名不变；`model.Config` 新增字段，旧配置文件没有这一项时解析成空串，兼容
- 实例之间交换的是 `View`，不含 `Config`，不影响互通
- 首次启动由 `GetDefault` 生成的配置文件会多一行 `board_url: ""`

# 对话2：微信正文不能换行，最多 20 个字

## 一、结论

对话1的「首行摘要 + 多行明细」方案不能用了，**整体撤回**。新方案的分工：

| 渠道 | 内容 |
|---|---|
| 微信正文（`te`） | 一句不超过 20 个字的摘要，不换行 |
| 点开消息（`board_url`） | 看板：各 URL 状态、健康条、「已告警 · 离线X」标签（`static/index.html:295`） |
| 日志 | 完整明细（确认实例数、始于、持续多久、第几次提醒、下次提醒间隔），用模板里的 `lg` 日志ID 能查到同一轮的日志（`SendWxMsg` 用的是同一个 ctx 的 logid，见 go_common `util/wechat.go` `hashMap["lg"]`） |

所以对话1补充的那些字段并没有丢，只是从微信正文挪进了日志。

## 二、正文格式

| 场景 | 格式 | 例子 |
|---|---|---|
| 1个离线 | `离线:<URL>` | `离线:s1.example.com/a…` |
| 多个离线 | `离线N:<URL>、<URL>` | `离线2:a.com、b.com` |
| 离线+恢复 | 离线在前，`；` 分隔 | `离线2:a、b:8080/x；恢复:c` |
| 资源超阈值 | 只列超了的项，取整 | `超阈值:CPU95%内存92%磁盘91%`（正好 20 个字） |
| 资源恢复 | 超阈值持续多久 | `资源恢复:超阈值1小时6分钟` |

几个取舍：
- **URL 去掉协议头和末尾的 `/`**（`trimUrl`）：20 个字里每个字都要省，这两部分基本区分不出什么
- **只有 1 个时不写个数**：省一个字给 URL
- **离线排在前面**：超长截断时，被截掉的是相对没那么要紧的恢复
- **兜底截断统一放在 `sendWxMsg`**：换行和连续空白压成一个空格；超过 20 个字时取前 19 个字再加 `…`；**按字（rune）数而不是字节数**，中文不会被切成乱码。三处发送都走这一个出口，以后改文案不会越界
- 仍然合并成一条消息，没有改成一个 URL 发一条：合并发送是最初的需求（`261001-213931-answer.md` 第 15 条），而且拆开发会成倍增加打扰

## 三、改动清单

| 文件 | 改动 |
|---|---|
| `service/alarm.go` | 新增常量 `wxTextLimit = 20`；新增 `sendWxMsg`（统一传 `board_url` 并截断）、`limitText`、`getSegment`、`getOverShort`；`trimScheme` 改为 `trimUrl`（再去掉末尾的 `/`）；`getUrlAlarmText` 改成单行摘要；明细改为写入日志字段 `offline`/`recover`/`detail` |
| `service/alarm_test.go` | `TestGetUrlAlarmText` 按新格式重写；新增 `TestLimitText`（换行、正好 20 个字、超长截断）、`TestGetOverShort` |

对话1的 `board_url` 配置项和相关测试保留不变。

## 四、验证

- `gofmt -l .`、`go vet ./...`：无输出
- `go test ./...`：全部通过

## 五、待确认

1. **「20 个字符」怎么算**：我按字数算的，一个汉字、一个英文字母都算 1 个。如果微信是按字节算，或者汉字算 2 个，需要告诉我，我再调整 `limitText`
2. **超出 20 个字时微信是自动截断还是直接拒绝发送**：我这边会先截断，所以两种情况都不会出问题；但如果微信是自动截断，就不需要我加的 `…`
3. 资源告警的正文里没法再写是哪台机器，只能靠模板的 `ip` 字段区分（对话1第五节第 3 点仍然有效）

# 对话3：30 个 URL、明细保留 7 天的内存占用

## 一、结论

按默认配置（`config/config.go`：`probe_interval_sec=2`、`probe_timeout_sec=5`、`record_window_sec=604800`），**30 个 URL 存满 7 天后，明细本身常驻约 1.4～4.6MB，算上 GC 还没回收的垃圾，堆的峰值大约 10MB**。在整个进程里这部分不大，不需要担心。

> 前提：我按默认配置算的，你实际的 `resource/survive_monitor.yaml` 我没看到。如果改过间隔、超时或窗口，按下面的公式代入即可。

## 二、推导（依据代码）

### 2.1 一条明细多大

- 明细只有 `service/view/view.go:32` 的 `records map[string][]model.Record` 这一处，每个 URL 一个切片
- `model.Record{Time int64; Alive bool}`，按 8 字节对齐后**每条 16 字节**
- 每探测一次 URL 写一条（`service/service.go` `probeUrls` → `view.SaveRecord`），所以**每个 URL 每轮一条**

### 2.2 一轮多长

根据 `service/service.go` `Monitor` 的注释和代码：串行探测，每个 URL 之后休眠 `probe_interval_sec`；然后采集资源，其中 CPU 采样阻塞 1 秒（`machine/machine.go` `cpuUsageInterval = time.Second`）；最后轮末再休眠一次。

```
一轮 ≈ 30 × (单次探测耗时 + 2) + 1 + 2  秒
```

| 情况 | 单次探测耗时 | 一轮 | 每个 URL 7 天的条数 | 30 个 URL 总条数 | 纯数据 |
|---|---|---|---|---|---|
| 全部秒回（上限） | ≈0 秒 | ≈63 秒 | 604800/63 ≈ 9,600 | 288,000 | **4.6MB** |
| 全部超时（下限） | 5 秒 | ≈213 秒 | ≈2,840 | 85,200 | **1.4MB** |

实际情况在两者之间，正常的服务都接近上限，所以**按 4.6MB 估算**（每个 URL 约 154KB）。

### 2.3 实测

我写了一个临时测试（跑完已删除），用 `SaveRecord` 给 30 个 URL 各写 9,600 条，`runtime.GC()` 之后读 `HeapAlloc`：

| 每个 URL 条数 | 总条数 | 切片总容量 | 增加的堆 |
|---|---|---|---|
| 9,600 | 288,000 | 337,920 | **5.36MB** |
| 2,840 | 85,200 | 107,520 | 1.72MB |

这是窗口还没存满、只追加的阶段，切片扩容会多留约 17% 的容量，所以比纯数据大一些。

### 2.4 存满之后（按代码推算，没有实测）

窗口存满后，每次 `SaveRecord` 都会：
1. `append` 一条，切片已满，触发扩容，**分配一次**
2. `trimRecords` 发现最老的一条过期，用 `append([]model.Record(nil), list[begin:]...)` 拷贝成新切片，**再分配一次**

所以：
- **常驻**：每个切片基本是紧凑大小，约等于纯数据 **4.6MB**
- **垃圾**：每次保存产生约 2 × 154KB，每轮 30 次约 9MB，**大约每分钟 9MB 的垃圾**
- **峰值**：Go 默认 `GOGC=100`，堆长到存活量的约 2 倍才触发 GC，所以**峰值约 9～10MB**；RSS 还要加上 Go 运行时、HTTP 客户端等基础开销，这部分和明细无关

### 2.5 其他内存（可以忽略）

| 数据 | 规模 |
|---|---|
| 本实例和对端快照（`selfSnapshot`/`peerSnapshots`） | 每个实例约 30 项 `Probes` 加上告警记录，每个实例几 KB |
| 看板健康条（`GetStatus` → `buildBar`） | 每次请求临时生成 30 × 96（`barSlotCount`）个 int，约 23KB，用完回收 |
| 探测响应体 | 每次最多读 4MB（`probe/probe.go` `maxBodySize`），用完回收；正常的对端视图只有几 KB |

## 三、可选优化（需要你决定，本轮没有改）

内存不是问题，真正值得关注的是 2.4 里**每次保存都拷贝整个切片**带来的分配和 GC 开销（约每分钟 9MB）。可选方案：

1. **最小改动**：`trimRecords` 不再每次拷贝，改为原地重新切片；过期部分超过一半时再拷贝一次。改动只在一个函数内
2. **彻底改**：看板只用 96 格健康条（`buildBar`），判定只用最近 `offline_round` 条（`converge`），所以原始明细其实可以直接按格聚合存储。内存能从 MB 级降到 KB 级，但要改 `SaveRecord`/`GetStatus`/`converge` 的数据结构，健康条的精度也会固定为写入时的格子划分

如果要做，我建议选 1。
