## 一、包结构（对标 jotcash）

排布轴 = 离外部多远；越靠根部越通用，内层不得被外层反向依赖。

| 包 | 位置 | 职责 | 业务逻辑 | 对标 jotcash |
| --- | --- | --- | --- | --- |
| `model` | 根部 | 数据契约：配置、快照、全局视图、资源、告警记录、枚举 | 无 | `model` |
| `config` | 根部 | 配置加载热更（`util.ConfigService`）+ 监听地址/路径/阈值常量 | 无 | `config` + `config/handler.go` |
| `probe` | 根部 | 外部适配：GET 单个 URL，判定在线/失败，解析对端视图 | 无 | `exchange_rate` |
| `resource` | 根部 | 外部适配：采集本机 CPU/内存/磁盘/负载 | 无 | `exchange_rate` |
| `handler` | 根部 | 协议入口：ping、status、静态页 | 无 | `handler` |
| `static` | 根部 | 前端 embed | 无 | `static` |
| `corn` | 根部 | 周期触发入口 | 无 | `corn` |
| `service` | 内层 | 业务编排：一轮探测、判定、告警、看板数据组装 | 全部 | `service` |
| `service/view` | 内层 | 全局视图读写（内存状态仓库，带业务校验） | 全部 | `service/repo` |

- **不建 `alarm` 包**：`util.SendWxMsg` 已是适配层，再包一层只是改名转发，属过度拆分；文案组装带业务规则，归 `service`。
- **不建 `tool` 包**：暂无「带本系统规则的纯工具」，按「过早设计深层包 = 设计跑在理解前面」不预留。
- **不建 `service/<能力>/<实现>`**：探测只有 HTTP 一种、告警只有微信一种，无多实现需求。

## 二、实现顺序

1. `model` → 2. `config` → 3. `probe` / `resource`（可并行） → 4. `service/view` → 5. `service` → 6. `handler` / `corn` → 7. `static`

## 三、数据契约（`model`）

- `Config`：`urls []string`（唯一必配项），其余阈值走默认常量兜底
- `Snapshot`：一个实例的一份快照 —— `source`（身份键）、`time`（原始产生时间）、`probes map[url]bool`（本实例对各 URL 的收敛结论）、`resource`、`alarms map[url]Alarm`
- `View`：对外形态 —— `snapshots map[source]Snapshot`，即 status 接口响应体的 data
- `Resource`：CPU/内存/磁盘/负载 + 采集时间
- `Alarm`：`startTime`（事件起始）+ `lastSendTime`（上次发送）
- `Record`：本地探测明细（URL、时间、是否在线），只供看板状态条，**不进交换载荷**

## 四、关键技术决策

### 4.1 周期调度用守护协程池，不用 cron

- `util.NewDaemonSingleGoPool(ctx, name, 间隔, 任务)`：底层是 `ants.NewPool(1)`，任务返回后才休眠再投下一轮
- 天然满足「上一轮未结束不开新一轮」，不需要额外互斥
- 旧代码用 `robfig/cron` 每分钟硬触发，日志实证轮次重叠（`logid=...010800000928` 到 01:09:23 仍在跑，下一轮已开始）
- 代价：`corn` 包名不再有 cron，保留是因为它在本仓与 jotcash 里已是「周期触发入口」的固定词

### 4.2 探测必须自建 HTTP 客户端

- 不能用 `util.NewHttpClientReq`：包级客户端是 `CreateHttpClient(3s, []{1s,2s,2s}, nil, true)`，带 3 次重试 + 4xx 会 `SetHttpBan(3s)`
- 后果就是旧代码的病根：单个失败点耗约 17 秒、封禁期内同 URL 直接失败
- 改用 `util.CreateHttpClient(超时, nil, nil, true)`：`sleeps` 为 nil 则不装重试条件、不设封禁

### 4.3 身份键由接收方回填

- 功能第 6 条要求「身份键 = 交换来源 URL」，但自己的快照无法自报（配置里认不出哪个 URL 是自己）
- 方案：**产出方把自己的 `source` 留空，接收方按「我从哪个 URL 拿到的」回填**
- 转发时只回填空值，已有 `source` 的原样透传 → 零配置，且不需要「本机对外 URL」这个配置项

### 4.4 识别对端用内容不用外壳

- 不靠 URL 形态判断是不是实例，靠「响应体能否解析出合规 `View`」
- 解析要穿透 `util.NewHttpRespByErr` 的 `{code,msg,data}` 外壳
- 识别条件严格到不会误认领，宁可不认领

### 4.5 并发探测与单轮预算

- 单轮用 `context.WithTimeout(ctx, 单轮预算)`，预算内并发 GET 全部 URL
- 并发用 `sync.WaitGroup` + 带缓冲 channel 限流，不引新依赖
- 超预算未完成的 URL 本轮记为失败（二值，已无「不确定」）

### 4.6 合并与过期

- 按 `source` 为键，`time` 新者胜；转发只读不改 `time`
- 判定分母 = `time` 未过期的全部 `Snapshot`；对端全过期时分母只剩自己，自动退化为「按自己的结论算」
- 「连续多轮失败」在各实例本地收敛后再广播，交换载荷里只有收敛结论

### 4.7 锁收敛到一处

- 全局视图是唯一共享状态，锁收敛在 `service/view` 一把读写锁上
- 看板读取取读锁，合并/写入取写锁 —— 对应规范第六层并发语义镜像
- 每个导出函数配非导出纯逻辑实现，复合操作复用非导出版本，避免重入锁

### 4.8 镜像对（设计自检）

| 正向 | 反向 | 验收 |
| --- | --- | --- |
| 组装本实例 `View` 产出响应 | 解析对端响应为 `View` | 往返恒等测试 |
| 写入自己的结论 | 合并对端的结论 | 同一入口骨架，仅锁与来源不同 |
| 发离线告警 | 发恢复通知 | 共用同一判定函数，生产侧服从判定侧 |
| 看板读视图 | 探测写视图 | 读锁/写锁对称 |

## 七、依赖欠缺与阻塞问题

### 阻塞 1｜go_common 没有资源采集能力

- `util/os.go` 只有 `GetServerName` / `GetHome` / `GetEnv` / `ExecCommand` 等，**全仓无 CPU/内存/磁盘/负载任何函数**（`grep -rln "cpu\|LoadAvg\|gopsutil" util/` 无业务命中）
- 直接阻塞功能第 8、11、18 条
- 三个选项：
  1. **推荐**：在 go_common 新增 `util.LoadResource`，底层用 `shirou/gopsutil/v4` —— 完全无业务逻辑、换项目照搬，按规范 1.4 就该沉到共享库
  2. 本项目建 `resource` 包直接引 gopsutil —— 能跑，但违反「能原样搬到下一个项目的沉到共享库」
  3. `util.ExecCommand` 读系统命令 —— 不跨平台、难测，不建议
- **需你决定走哪条**；选 1 则本轮要先在 go_common 动工

### 阻塞 2｜Go 版本必须升到 1.27

- go_common HEAD 的 `go.mod` 声明 `go 1.27`
- survive_monitor 现为 `go 1.24`，Dockerfile 基础镜像 `golang:1.24-alpine`
- 两处都要升，否则 `go get` 直接失败

### 阻塞 3｜微信模板字段变了

- `util.SendWxMsg` 固定写入 `sn` / `ip` / `lg` / `te` 四个字段（`util/wechat.go`）
- 旧 msg_gateway 用的是 `logid` / `sn` / `ip` / `text`
- 公众号模板未按新字段改，发送会失败
- **需你确认模板已更新**

### 阻塞 4｜微信凭据环境变量要注入

- 必需：`wx_app_id`、`wx_secret`
- 可选：`wx_open_id`（留空则查订阅者列表取最早关注者）、`wx_template_id`（留空则取模板列表第一个）
- 现有 Dockerfile 无任何 `ENV` 注入，部署脚本要补
- 这是旧代码告警静默失败的同一类问题（日志 `初始化SDK，参数为空`）

### 阻塞 5｜告警通道没有可观测性

- `util.SendWxMsg` 返回 `error`，比旧 `sdk.SendTemplateText`（无返回值）好
- 但功能第 12 条「发送成功才记入已发告警」已经把重试交给轮询，**没有任何地方会告诉你通道坏了**
- 对话6 已明确不做通道自检，此处仅记录风险：凭据配错时服务会安静地永远发不出告警
- 不改功能，但建议发送失败按 Error 级别记日志（`util.SendWxMsg` 内部已这么做）
