# 对话1：磁盘显示「136KB / 7.5GB」

## 结论：采集没算错，是采错了盘

前端 `static/index.html` 的 `formatSize` 是标准的 1024 进制换算，数值原样来自后端；后端 `machine.LoadResource` 调 `go_common/util.GetDiskTotal/GetDiskUsed`，内部是 gopsutil `disk.UsageWithContext(path)`（即 statfs），取的 `Total`/`Used` 与 `df` 同口径。计算链路本身没有问题。

问题在**被采集的路径**。`resource/survive_monitor.yaml` 里 `disk_path: ~`，由 `config/config.go` 的 `fillConfig` 补成默认值 `diskPath = "/"`。而本机服务跑在 GoLand 的 flatpak 沙箱里（已确认：存在 `/.flatpak-info`，1 号进程是 `bwrap`），沙箱的根目录是一块 tmpfs：

```
$ findmnt /
/  tmpfs[/newroot]  tmpfs
$ df -h /
tmpfs  7.6G  136K  7.6G  1% /
```

136K 已用、7.6G 总量（df 向上取整，页面 `toFixed(1)` 显示 7.5GB）—— 与页面上的数字逐项对得上。页面显示的就是这块内存盘，不是磁盘。项目所在的真实磁盘是 `/dev/nvme0n1p3`（btrfs，挂在 `/home`，466G/245G）。

| 项 | 状态 |
| --- | --- |
| 页面数字来自 flatpak 沙箱根目录的 tmpfs | 已确认（findmnt/df 与页面一致） |
| Docker 部署不受影响 | 已确认：容器根目录是 overlay，不在内存盘列表里，不触发回退，行为与修改前一致 |
| 其他部署环境（裸机 systemd 等） | 根目录不是 tmpfs，不触发回退，行为不变 |

## 方案取舍

| 方案 | 取舍 |
| --- | --- |
| A. 把默认 `diskPath` 从 `/` 改成工作目录 `.` | 改动最小，但会改变正常主机上的口径（`/` 和 `/home` 分区不同时就从根分区变成了数据分区），不采用 |
| B. 只改本机配置 `disk_path` | 治标；换个沙箱/内存根的环境又会复现，不采用 |
| **C. 配置路径落在内存型文件系统（tmpfs/ramfs/devtmpfs）上时，回退到工作目录** | **采用**。只在「量到的是内存盘」这种明显错误的场景才介入，正常环境零变化；工作目录放着 `resource/` 配置和 `log/` 日志，它所在的分区就是本服务真正依赖的磁盘 |

回退的保护条件：工作目录也是内存盘，或取不到文件系统类型，则原样使用配置路径；路径不存在的错误仍由后面的采集照常报出（`TestLoadResourceIllegalPath` 行为不变）。

回退后「实际量的路径」与配置不再一致，所以把实际路径带进了资源数据，告警文案也改用它，避免告警里写着 `路径/` 实际量的是别处。

## 改动

| 文件 | 改动 |
| --- | --- |
| `machine/machine.go` | 新增 `resolveDiskPath` / `isMemoryFs` 与 `memoryFsTypes`；`LoadResource` 先解析实际路径再采集，并写入 `resource.DiskPath`。回退时打一条 Warn（`采集磁盘，配置路径是内存盘，回退到工作目录`），用 `sync.Map` 按配置路径去重，避免每分钟一轮刷屏 |
| `model/resource.go` | `Resource` 新增 `DiskPath string json:"disk_path"`，实际采集的磁盘路径。新增字段对实例间快照交换向前/向后兼容（旧实例忽略、读旧实例得空串） |
| `service/alarm.go` | `getOverTexts` 磁盘文案的路径由 `conf.DiskPath` 改为 `resource.DiskPath` |
| `go.mod` | `github.com/shirou/gopsutil/v4 v4.26.9` 由 indirect 转为直接依赖（`go mod tidy` 结果，版本不变，go.sum 无变化）。`go_common/util` 只暴露总量/已用，不暴露文件系统类型，所以直接用 gopsutil 取 `Fstype` |
| `machine/machine_test.go` | 新增 `TestResolveDiskPathMemoryFs`（`/dev/shm` 应回退到工作目录，且 `LoadResource` 上报的 `DiskPath` 一致）、`TestResolveDiskPathKeep`（非内存盘、取不到类型的路径原样返回） |
| `service/alarm_test.go` | `TestGetOverTexts` 补断言：磁盘文案带的是 `resource.DiskPath` |

前端未改：`disk_used/disk_total` 字段不变，数据修正后页面自然正确。没有给页面加「采集路径」展示——页面目前没有 HTML 转义工具，而快照会来自对端实例，直接拼路径进 HTML 有注入面，不值得为此扩大范围。如需展示可后续加转义后再做。

## 验证

- `gofmt -l .` 无输出，`go vet ./...` 通过，`go test -count=1 ./...` 全部通过
- 实机端到端：在本沙箱内用默认路径 `/` 调 `LoadResource`：
  - 修改前：已用 136KB / 总量 7.5GB（tmpfs）
  - 修改后：`DiskPath=/home/ms/document/code/survive_monitor/machine`（测试工作目录），`used=262108717056 total=499982008320`
  - 对照 `df -B1 .`：`262108717056 499982008320 /home` —— **逐字节一致**，页面将显示约「244.1GB / 465.6GB」
- 临时验证用的测试文件与测试产生的 `machine/log` 已清理；未提交变更

## 需要注意

- 服务重启后生效（采集代码变更）

# 对话2：资源数据多久采集一次、用什么机制循环

## 结论

- **间隔**：配置项 `probe_interval_sec`，默认 60 秒（`config/config.go` 常量 `probeIntervalSec = 60`；`resource/survive_monitor.yaml` 当前也是 `probe_interval_sec: 60`）。**资源采集没有独立的间隔**，它是监听轮次 `service.Monitor` 中的一步，与 URL 探测同一节奏。
- **机制**：不是 cron，也不是 `time.Ticker`，而是 go_common 的**守护单协程池** `util.NewDaemonSingleGoPool`（底层是容量为 1 的 `ants` 协程池）：跑完一轮 → 休眠 60 秒 → 再投下一轮。
- **实际周期 = 一轮执行耗时 + 60 秒**，不是严格的 60 秒。

## 调用链（已确认）

```
main.main
 └─ corn.Init                                     corn/corn.go
     interval = config.GetConfig(ctx).ProbeIntervalSec 秒   ← 启动时只读一次
     util.NewDaemonSingleGoPool(ctx, "Monitor", interval, monitor)
      └─ monitor：每轮 util.GenCtx() 换新日志ID → service.Monitor(ctx)
          └─ service.Monitor                       service/service.go
              1. URL列表为空 → Warn后直接return（本轮不采资源！）
              2. probeUrls（受 probe_budget_sec=45s 预算约束）
              3. view.Converge 收敛探测结论
              4. machine.LoadResource(ctx, conf.DiskPath)   ← 资源采集就在这里
              5. view.SaveSelf(ctx, probes, &resource)       写入本实例快照
              6. 合并对端视图 → alarmUrl → alarmResource → view.Clean
```

`machine.LoadResource` 全项目只有 `service/service.go:32` 这一个调用点，没有别的采集入口。

## 守护单协程池的循环方式（go_common `util/sync.go`）

1. `NewSingleGoPool`：`ants.NewPool(1, ants.WithMaxBlockingTasks(1))`，池里只有 1 个工作协程（第 57 行）
2. `AddDaemonTask` → `addDaemonTask`：把任务 `Submit` 进池子**立即执行**，所以服务启动后第一轮马上就跑，不会先等 60 秒（第 135 行）
3. 任务函数的 `defer Defer(...)` 里另起一个协程：`Sleep(ctx, sleep)` 睡满间隔 → 检查 ctx 未取消 → 递归调用 `addDaemonTask` 投下一轮（第 97–119 行）
4. 下一轮是在**上一轮结束后**才开始计时，天然保证不会出现两轮重叠；`corn/corn.go` 的注释也写明了选它而不选 cron 就是这个原因
5. `Defer` 会兜住 panic：某一轮 panic 只记一条 Error 日志「单协程池，退出」，下一轮照常调度，循环不会因此中断
6. `Sleep` 同时监听 `ctx.Done()`，取消时立即退出；本项目不会主动 Cancel 这个池子，所以它跟进程同生共死

## 实际周期验证（日志）

`log/survive_monitor/log.log` 里每轮结束都会打一条「单协程池，退出」，最近三轮：

| 结束时间 | 与上一轮相隔 |
| --- | --- |
| 2026-10-02 10:36:17 | — |
| 2026-10-02 10:37:23 | 66 秒 |
| 2026-10-02 10:38:33 | 70 秒 |

即 60 秒休眠 + 6～10 秒执行。每轮执行耗时主要来自：

- URL 探测：最长受 `probe_budget_sec`（默认 45 秒）约束，有超时的 URL 时会接近这个上限
- CPU 使用率采样：`machine.cpuUsageInterval = time.Second`，固定阻塞 1 秒
- 其余（内存、磁盘、合并、告警）都是毫秒级

所以理论范围大约是 **61 秒～106 秒多一轮**（探测超过预算会被掐断，最坏约 60 + 45 + 1 + 告警发送耗时）。

## 需要注意的几点

| 项 | 说明 | 依据 |
| --- | --- | --- |
| URL 列表为空时不采集资源 | `service.Monitor` 开头 `len(conf.Urls) == 0` 直接 return，资源采集、资源告警都被跳过，页面上的资源会停留在旧值或为空 | `service/service.go:20-23` |
| 改间隔要重启 | `ProbeIntervalSec` 只在 `corn.Init` 读一次，热加载配置不会改变运行中的间隔 | `corn/corn.go:16`；`model/config.go` 字段注释「服务启动时读一次，改完要重启」 |
| 资源是点状快照 | 内存、磁盘是采集时刻的值；CPU 是这 1 秒窗口的平均使用率，不是两轮之间的平均 | `machine/machine.go` |
| 资源告警需要连续 N 轮 | `resource_round` 默认 3，结合实际周期，超阈值约 3～5 分钟后才会告警 | `config/config.go` `resourceRound = 3` |

本轮只做分析，未改动代码。

# 对话3：`probe` 的含义；URL 列表为空也要采集资源

## 一、`probe` 是什么意思

英文 probe 本义是「探针、试探」，运维监控里专指**探活**：主动向目标发一次请求，根据有没有正常响应判断它是否存活（类似 Kubernetes 的 liveness probe）。本项目里统一译作「探测」，日志、注释都用这个词。

在本项目中 probe 指的就是**对配置里每个 URL 发一次 HTTP GET，判定它在线还是离线**，顺带尝试从响应里认领对端实例的全局视图。

### 判定规则（`probe/probe.go` `Probe`）

| 情况 | 结论 |
| --- | --- |
| 请求出错（连不上、超时等）或响应为空 | 离线 |
| 响应码 `<= 0` 或 `>= 500` | 离线 |
| 其他响应码（含 2xx/3xx/4xx） | 在线 |
| 在线且响应体能被 `ParseView` 解析成本服务的全局视图（外壳 `code == 200` 且 `snapshots` 非空） | 在线，并返回对端视图用于合并 |

单次探测只发一次请求、不重试（`getClient` 注释：重试会拖长单轮，封禁会凭空多一次失败）。

### 项目里带 probe 的名字

| 名字 | 位置 | 含义 |
| --- | --- | --- |
| `probe` 包 / `probe.Probe` | `probe/probe.go` | 探测单个 URL |
| `probeUrls` | `service/service.go` | 一轮内并发探测全部 URL，落明细、收集对端视图 |
| `Snapshot.Probes` | `model/snapshot.go` | `URL -> 本实例是否认为它在线`，已是连续多轮收敛后的结论，不是单次结果 |
| `probe_interval_sec` | `model/config.go` | 监听轮次间隔（资源采集也跟着这个节奏，见对话2） |
| `probe_budget_sec` | 同上 | 单轮探测总预算，超时未完成的 URL 按失败计 |
| `probe_timeout_sec` | 同上 | 单次探测超时 |
| `probe_concurrency` | 同上 | 探测并发数 |

单次探测结果是 `model.Record`（`alive`），落在看板明细里；连续 `offline_round` 轮都失败才收敛成离线（`view.Converge`）。

## 二、URL 列表为空也要采集资源

### 现状（对话2 已指出）

`service.Monitor` 开头 `len(conf.Urls) == 0` 时打一条 Warn 就 `return`，资源采集、资源告警、`view.Clean` 全部被跳过。

### 方案

去掉提前 `return`，只保留 Warn。逐步核对过空列表下后续每一步的行为，都安全，无需额外分支：

| 步骤 | 空列表下的行为 | 依据 |
| --- | --- | --- |
| `probeUrls` | `for` 零次，`group.Wait()` 立即返回，返回空 map | `service/service.go` |
| `view.Converge` | 返回空 map | `service/view/view.go` |
| `machine.LoadResource` | **照常采集** | — |
| `view.SaveSelf` | 落下空的 `Probes` + 本轮资源 | 同上 |
| 合并对端视图 | `views` 为空，不合并 | — |
| `alarmUrl` → `judgeAlarm` | 遍历 `conf.Urls` 零次，无文案直接 return，不发消息 | `service/alarm.go` |
| `alarmResource` | **照常判定、照常告警** | 同上 |
| `view.Clean` | 照常清理过期快照与窗口外明细（顺带修正：以前 URL 被清空后旧明细不会被清理） | `service/view/view.go` |

为了能测这条路径，把 `Monitor` 拆成两层：`Monitor(ctx)` 读配置后调用 `monitor(ctx, conf)`，对外签名不变（`corn/corn.go` 仍调 `service.Monitor`）。

### 改动

| 文件 | 改动 |
| --- | --- |
| `service/service.go` | 新增 `monitor(ctx, conf)` 承载原逻辑；URL 为空时只打 Warn「监听一轮，URL列表为空，只采集本机资源」，不再 return |
| `service/service_test.go` | 新增 `TestMonitorEmptyUrls`：空 URL 列表跑一轮，断言自己的快照存在、资源已采到且取值合法、`Probes` 为空。阈值设为 1000，保证测试不会真的发微信告警 |

### 副作用评估

- URL 为空时每轮仍有一条 Warn，与改动前频率相同（改动前也是每轮一条）
- 空列表时本实例不会主动去拉对端视图（没有 URL 可探），但仍会通过 `/api/view` 被对端拉取，资源能出现在对端看板上——这正是这次改动的收益
- 首次启动配置文件自动生成、URL 为空的场景（`config/config.go` `Parse` 的注释），现在也能立刻在看板看到本机资源

### 验证

- `gofmt -l .` 无输出，`go vet ./...` 通过，`go test -count=1 ./...` 全部通过
- `TestMonitorEmptyUrls` 通过
- 无临时文件残留；未提交变更
