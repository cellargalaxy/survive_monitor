# 对话1：服务功能重新梳理（产品视角）

> 本轮不涉及代码与技术实现，只做产品功能的重新定义与简化。
> 所有「现状」结论均标注代码/配置/日志依据；无法从现有资料推断的，统一进入文末「待确认清单」。

## 一、结论先行

你给的方向是对的，但有四处需要在产品层面先纠正，否则重构后问题依旧存在：

1. **必须显式建模「服务器」这个对象**。现在配置里只有一维 URL 列表（`model/config.go` 的 `Urls []string`），判定整机离线靠 `service/service.go:groupURLsByDomain` 按「协议+域名」分组。域名 ≠ 服务器：同一台机器挂多个域名会被拆成多组，不同机器也无法确认是否同机。不显式声明「服务归属哪台服务器」，就永远无法可靠区分「单服务离线」和「整机离线」。
2. **探测结论必须从「二值」改成「三值」**。现在只有 `alive bool`（`service/service.go:StatusRecord.Alive`），超时和连接被拒被当成同一件事。你描述的「有的实例看到服务是活的、有的看到 HTTP 超时」，本质就是把「不确定」误当成了「离线」。
3. **实例之间要交换的不是心跳，而是「探测结论」**。现在配置里只是把对端的 `.../survive_monitor/api/ping` 当成普通 URL 探测（`resource/survive_monitor.yaml` 中 wstbd、gcloug 两处），实例之间只会互相探活，不会互相比对结论，所以每个实例都独立告警 —— 误报和重复告警都源于此。
4. **你还有一个比误报更严重的问题：告警其实发不出去，而且没人知道**。日志里大量 `发送模板消息，查询模板为空`（根因 `初始化SDK，参数为空`），说明那段时间的告警一条都没真正送达；而 `sdk.SendTemplateText` 没有返回值，调用方也不检查 —— 服务「以为」自己告警了。这一条直接击穿本服务的唯一成功标准，优先级高于误报治理。详见 E5。

在此基础上，功能收敛为 **5 个功能域**：监控对象管理、服务存活探测、服务器资源采集、离线判定与收敛、告警投递与状态看板。

## 二、产品定位与唯一成功标准

**survive_monitor 是一个去中心化的「离线告警器」**，不是监控平台。

来自任务 Prompt 的唯一成功标准：

> 假设不会全部服务器都在短时间内同时下线，只要有一个服务器还正常运行，它监听到其他服务下线，能发送出告警消息，就算达到目标。

因此所有功能设计只服务两个目标，优先级固定：

| 优先级 | 目标 | 含义 |
| --- | --- | --- |
| P0 | **告警必达** | 不漏报。任一存活实例都有独立发出告警的能力，不依赖任何中心节点 |
| P1 | **告警可信** | 不误报。不可信的观测不得升级为告警 |

两者冲突时（例如全网只剩一个实例、无法交叉验证），**以 P0 为准：宁可误报，不可漏报**。这是一个取舍点，见「待确认清单」第 4 条。

## 三、对象模型（产品概念，共 4 个）

重构的第一件事是把「一堆 URL」换成有层次的对象：

| 对象 | 说明 | 现状 |
| --- | --- | --- |
| **服务器（节点）** | 一台物理/虚拟机，有稳定的名字。标记它是否部署了本服务实例 | **完全缺失**，只能靠域名近似 |
| **服务** | 跑在某台服务器上的一个服务，**必须显式声明归属的服务器** | 隐含在 URL 里，归属关系靠域名推断 |
| **探测点** | 一个服务对外暴露的一个可探测地址，一个服务可有多个 | 对应现在的单条 URL |
| **实例** | 本服务自身的一个部署，跑在某台服务器上，既是探测者也是被探测者 | 混在 `Urls` 里当普通探测点（wstbd、gcloug） |

关键约束：**所有实例共用同一份对象清单**。跨实例比对结论的前提是大家在谈论同一个对象，配置不一致则共识无意义。

## 四、功能域 A：服务存活探测

### A1. 探测结论三值化（误报治理的产品基础）

| 结论 | 判定来源 | 是否可触发告警 |
| --- | --- | --- |
| **在线** | 探测明确成功 | — |
| **离线** | 明确失败：连接被拒、DNS 解析失败、TLS 握手失败、持续 5xx | 可以 |
| **不确定** | 超时、探测方自身网络异常、本轮未执行 | **不可以**，只延长观察窗口 |

依据：日志中真实的失败形态是 `err: Get "https://wstbd.../": context deadline exceeded (Client.Timeout exceeded while awaiting headers)`（`log/260208010227359270/log.log`），而默认超时只有 3 秒（`vendor/.../go_common/util/http.go:TimeoutDefault = time.Second * 3`）。超时是「我没看清」，不是「它死了」，现在却被 `monitorSurvive` 直接记成 `alive=false`。

### A2. 单实例内的确认机制

单次失败不构成结论，需连续多次失败（跨若干探测周期）才形成「本实例判定离线」。

现状：`service/service.go:MonitorSurvive` 的 `for i := 0; i < 1; i++` 只会执行一次，循环体末尾的 `time.Sleep(time.Second)` 是永远执行不到的死代码 —— 应用层**没有**重试确认；真正的重试发生在 HTTP 客户端内部（`GetHttpClientSpider` → `CreateHttpClient(3s, 0, SpiderSleepDefault=[0,2s,2s], ...)`，共 4 次尝试），但这个重试对「超时」和「离线」不加区分，且对产品不可见、不可配。

### A3. 探测方自检（新增，重要）

每个实例在每轮结束后先评估**自己**是否可信：若本轮对「分布在多台不同服务器上的目标」普遍失败，则更可能是本实例自身的网络出了问题。此时本轮全部结论降级为「不确定」，不参与告警，并对其他实例声明「我本轮不可信」。

依据：日志中 wstbd 域名下 5 个探测点在 01:07–01:12 连续 5 个轮次里**全部**失败（`log/260208010227359270/log.log`，每个探测点各 5 次 `检测存活，请求异常`），而同期 clcone / gcloug / cgwarich 的 8 个探测点**全部正常**。这种「单台机器成片失败、其余机器完好」既可能是真整机离线，也可能是探测方到该机器的链路抖动，**单实例无法区分**，只能靠自检 + 跨实例比对。反之若某一轮里**所有服务器**的探测点都失败，则几乎可以断定是探测方自己的问题。

### A4. 「存活」的产品定义需要收口

现状 `monitorSurvive` 的判定是 `statusCode > 0 && statusCode < 500`，即 **404 被视为在线**。另外 HTTP 客户端对非 404 的 4xx 会把该地址短时封禁（`util/http.go` 中 `setHttpBan(ctx, response.Request.URL, SleepDefault)`，3 秒），封禁期内请求直接返回 `HttpBan` 错误 → 在产品侧表现为「离线」。这两条规则一个过宽、一个过严，是独立于超时之外的第二类误报源。产品上需要明确：哪些响应算「服务还活着」。见「待确认清单」第 7 条。

### A5. 发现时延必须可预期，探测轮次不得堆叠

产品上要承诺「多久能发现离线」，而现在这个时延是失控的。

依据（`log/260208010227359270/log.log`）：

| 场景 | 单轮探测 13 个点的实际耗时 |
| --- | --- |
| 全部正常 | 约 3～12 秒（如 01:26:00 → 01:26:03、01:25:00 → 01:25:12） |
| wstbd 整组失败 | **单个失败点约 17 秒**，仅 wstbd 5 个点就耗 85 秒以上（01:08:16 → 01:09:23） |

后果是轮次开始重叠：`logid=260208010800000928` 这一轮到 01:09:23 还在记录失败，而 `logid=260208010900000863` 这一轮已经在 01:09:23 开始失败了。cron 配的是每分钟一轮（`resource/survive_monitor.yaml` 的 `cron: "*/1 * * * *"`），但失败时一轮根本跑不完 —— 探测点越多、失败越多，堆叠越严重，「每分钟一轮」就越是一句空话。

产品要求：

1. 单轮必须有**时间预算上限**，超预算未完成的探测点记为「不确定」，而不是让轮次无限拖长
2. 上一轮未结束时，新一轮不得叠加执行
3. 探测点数量增长不应线性拉长单轮耗时（并发探测）
4. 对外明确承诺「发现时延 = 探测周期 × 确认轮次 + 共识耗时」的上限

这一条同时决定了第十二章第 8 条的答案空间。

## 五、功能域 B：服务器资源采集（新增）

### B1. 双重产品价值

资源采集不只是「看指标」，它同时是**判定整机离线的权威信号**：

1. **容量告警**：指标持续超阈值一段时间才告警（避免瞬时毛刺触发）
2. **整机心跳**：资源上报中断 = 整机离线的直接证据。比「这台机器下所有服务都探测失败」更快、更直接、更难误报 —— 后者可能是反向代理挂了，前者几乎只能是机器本身没了

### B2. 覆盖范围的硬限制

资源只能采自**部署了本服务实例的服务器**。配置中 `https://cgwarich.cellargalaxy.ddns-ip.net/api/v1/health` 只有一个 health 探测点、没有 survive_monitor 的 ping 端点，说明现实中存在「无实例服务器」。对这类机器只能退回用「其下所有服务均离线」来推断整机离线，判定会更慢也更不准。见「待确认清单」第 2 条。

### B3. 采集项与保留策略

建议最小集：CPU 使用率、内存使用率、磁盘使用率（分挂载点）、系统负载、实例启动时间/运行时长、本实例网络自检结果。具体项与阈值见「待确认清单」第 3 条。

资源数据同样**不持久化**，只保留内存滑窗，供趋势判断与看板使用。

## 六、功能域 C：多实例互监听

### C1. 实例之间交换什么

每轮探测后，实例之间互相拉取/推送三样东西：

1. **本轮探测结论**（每个探测点：在线/离线/不确定 + 失败形态）
2. **本机资源快照**
3. **已发送的告警事件指纹**（用于去重，见 E2）

每个实例据此在内存里维护一份**全局视图**：所有服务器、服务、实例的最新状态（自己的观测 + 对端的观测）。纯内存，重启即丢，重建只需一两个探测周期。

### C2. 为什么这不是「选举算法」

任务 Prompt 明确要求「不做任何选举算法」。本设计确实不做：

- **没有主节点、没有租约、没有任期**，所有实例完全对等
- 跨实例一致不靠「选一个人拍板」，而靠**所有实例按同一套规则、对同一份证据各自独立计算**，自然得到相同结论
- 告警去重不靠「选出发送者」，而靠**事件指纹广播**：谁先判定成立谁就发，发完把指纹告诉别人；别人看到指纹就不再发。协商失败时允许重复发送（重复 ≤ 漏报）

### C3. 实例自身也是被监控对象

实例是跑在服务器上的服务，天然进入服务级监控。实例离线要告警，且它同时意味着「那台服务器的资源心跳中断」。

### C4. 退化模式

当一个实例拿不到任何对端数据（对端全挂，或自己被网络隔离）时，按自己的结论直接告警。这正是 Prompt 中「只要有一个服务器还正常运行就能发出告警」的兜底路径。代价是：被网络隔离的实例会误报。

## 七、功能域 D：离线判定与收敛

四级门槛，自下而上收敛：

| 层级 | 输入 | 输出 | 对应小节 |
| --- | --- | --- | --- |
| L1 单次探测 | 一次请求结果 | 在线/离线/不确定 | A1 |
| L2 单实例判定 | 同一探测点连续多轮的 L1 结果 | 本实例认为「离线」 | A2 |
| L3 实例可信度 | 本实例本轮全部 L1 结果 | 本轮是否可信 | A3 |
| L4 跨实例共识 | 各可信实例的 L2 结论 | 事件成立 | C1 |

L4 成立后，再做**归因**，这是「单服务离线」与「整机离线」的分界：

- **整机离线**：该服务器资源心跳中断，**或**其下全部（绝大多数）服务同时判定离线
  → 只发一条「服务器离线」告警，**其下所有服务的离线告警全部被收敛掉**
- **服务离线**：同一服务器下只有部分服务离线
  → 按服务器聚合成一条消息发出

现状只有后者的雏形：`MonitorConfig` 按域名聚合、一个域名一条消息（`服务离线 [%s]\n%s`），完全没有「整机离线」这个概念，机器挂掉时会按域名数量发多条「服务离线」，且不会告诉你「是整台机器没了」。

## 八、功能域 E：告警投递与状态看板

### E1. 告警状态机（治理重复告警）

现状：`MonitorConfig` 在每个 cron tick（配置 `cron: "*/1 * * * *"`，每分钟）只要仍处离线就调用一次 `sdk.SendTemplateText` —— 无状态机、无退避、**无恢复通知**。一台机器挂一晚上会收到几百条相同消息。

目标状态机：

```
在线 ──判定离线──> 告警一次
                    │
                    ├─ 持续离线 ──> 按退避降频提醒（如 5min / 30min / 2h）
                    │
                    └─ 恢复 ──────> 发送恢复通知，回到「在线」
```

### E2. 跨实例去重

事件指纹 = 对象（服务器/服务）+ 状态 + 事件起始时间。实例间同步已发送的指纹；见过的不再发。协商不可用时允许重复。

### E3. 告警分级与聚合

**服务器离线 > 服务离线 > 资源阈值**。同一服务器的同级事件合并为一条消息。消息里要能一眼看出：哪台机器、哪些服务、什么时候开始、几个实例确认过（后者是可信度的直接体现）。

### E4. 告警通道可达性（风险项）

现在是单通道：`config.Config.BoardUrl` + msg_gateway（`sdk.SendTemplateText(ctx, "通用消息", config.Config.BoardUrl, msg)`）。如果 msg_gateway 自身部署在被监控的服务器上，整机离线时告警可能根本发不出去 —— 这会直接击穿 P0「告警必达」。见「待确认清单」第 5 条。

### E5. 告警投递结果必须可观测（现状是静默失败）

**这是当前最严重的问题，直接击穿 P0。**

依据：日志里大量 `发送模板消息，查询模板为空`，根因是 `初始化SDK，参数为空`（`vendor/.../msg_gateway/sdk/sdk.go:42`，`InitSdk` 要求 `wx_app_id` / `wx_secret` 两个环境变量，取自 `util.GetEnv`）。也就是说**那段时间里所有告警都没有真正发出去**。

而 `sdk.SendTemplateText` 没有返回值（`vendor/.../sdk/template_message.go:66`），`service/service.go:MonitorConfig` 调用后不检查任何结果 —— 服务「以为」自己告警了，实际一条都没发出，且没有任何机制能发现这件事。

产品要求：

1. 告警投递要有明确的成功/失败结论，失败要重试
2. 告警通道配置缺失或失效时，**启动即报错**，不能等到真出事才发现发不出去
3. 投递失败要以其他可见方式暴露（至少在状态看板上标红「告警通道不可用」）
4. 通道可用性本身要被周期性自检，而不是只在有告警时才知道

### E6. 状态看板

保留现有能力（`controller/status.go` 的 `/api/status` + `static/html/status.html`：状态时间线、可用率、最近检测时间），做三处产品调整：

1. 展示维度从「URL 列表」升级为「服务器 → 服务 → 探测点」三层，并展示资源指标与实例健康
2. 任意实例都展示**全局视图**（含对端观测），而不是只展示自己的探测结果
3. 收紧内存窗口：现在 `CleanOldRecords` 保留 7 天，按每分钟每 URL 一条、13 个探测点算约 13 万条记录常驻内存，且随探测点增加线性膨胀。看板本身是按时间槽位渲染的（`buildSlots`），不需要原始密度。见「待确认清单」第 6 条

## 九、明确不做的事（范围边界）

| 不做 | 依据 |
| --- | --- |
| 任何数据持久化（DB / 文件 / 外部存储） | 任务 Prompt 明确要求 |
| 选举算法、主节点、强一致 | 任务 Prompt 明确要求；替代方案见 C2 |
| 自动恢复动作（重启服务、执行运维脚本） | 超出「监听 + 告警」定位，见待确认第 9 条 |
| 日志采集 / 链路追踪 / APM | 不是本服务定位 |
| 权限与多租户体系 | 现有 `util.GetClaims(c)` 仅用于日志记录，无实际鉴权 |
| 值班表、告警升级链路、工单对接 | 超出当前规模 |

| 功能点 | 现状（代码依据） | 目标 | 变化 |

## 十一、方案取舍记录

| 取舍点 | 选择 | 理由 | 代价 |
| --- | --- | --- | --- |
| 整机离线判定主信号 | 资源心跳中断为主，服务成片离线为辅 | 心跳是机器级直接证据；成片离线可能只是反代挂了 | 无实例的服务器（如 cgwarich）只能用辅信号 |
| 跨实例一致性 | 同规则独立计算 + 指纹去重 | 满足「不做选举」约束，且无中心节点依赖 | 极端情况下重复告警 |
| 单实例退化 | 允许单实例独立告警 | 守住 P0 告警必达 | 被网络隔离的实例会误报 |
| 超时的处理 | 归入「不确定」，不直接告警 | 这是当前误报的主因（日志中失败形态全为 `context deadline exceeded`） | 真实离线的发现会慢一到两个周期 |
| 历史数据 | 内存滑窗，不持久化 | 任务 Prompt 硬约束 | 重启后看板历史清零 |
